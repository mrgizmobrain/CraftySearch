# Crafty Search — Design Spec

*Status: draft v3, Nov 5 2026. Inspired by ClientStorage (crafting from storage) and ChestTracker (storage memory and UI).*

## 1. Summary

Crafty Search is a Fabric mod for Minecraft 26.2. It lets you search, count and craft from the items in nearby storage without opening chests by hand.

- **Client-first:** works on any server with only the client installed. On a server without the mod, crafting is limited to chests within reach.
- **Optional server part:** the same jar, installed on a server, gives full-radius live data and crafting. Singleplayer always gets this mode, because the singleplayer world runs on a built-in server that loads the mod too.
- **Vanilla-native crafting:** uses the vanilla recipe book and its "place recipe" mechanism instead of a custom crafting UI.

## 3. Features (v1)

### 3.1 Storage panel
- Appears on the **right side** of:
  - the survival **player inventory** screen (2x2 grid), and
  - the **crafting table** screen (3x3 grid).
- **Can be hidden, like the vanilla recipe book.** A toggle button next to the grid shows or hides the panel. Each screen remembers its own state (inventory and crafting table separately) across sessions, the same way the recipe book remembers whether it's open. Crafting from storage keeps working while the panel is hidden, because the recipe book still drives it.
- Can also be opened anywhere as a full screen with a keybind, for searching and viewing totals.
- Shows **totals per item** across all storage within the configured radius, plus the player's inventory. Memory stores full items, data components included. Tiles are grouped by item plus components, so differently enchanted books, potions and renamed items get their own tiles, but durability and anvil repair cost are ignored, so worn copies of a tool share one tile. Hovering a tile shows the vanilla item tooltip (enchantments, effects) plus totals. (Decided Nov 6.)
- Has a search bar with ChestTracker-style filters: `#tag`, `@modid`, and plain text, which matches the item name and any enchantment name on it, such as `mending`. A number right after a word means that enchantment at exactly that level: `sharpness 1` finds only Sharpness I. A number on its own matches any enchantment at that level. Roman numerals are treated as plain letters. The empty box shows the hint "Search #tag @mod", or just "Search" where the panel is too narrow for it (the edit box doesn't clip hints; Nov 7).
- **Clicking an item highlights the chests that contain it** in the world, with an outline visible through walls and a timeout. Opening one of those chests drops its outline, so the remaining outlines show where you haven't looked.
- **Slot highlight:** a container opened while that search is active marks the slots holding the searched item with a soft tint and thin edge drawn behind the item and its count, matched by item and components (ignoring durability). The highlight stays until that screen closes, even if the world outlines expire meanwhile.
- Adapts to screen space: when the window is too narrow or the GUI scale is too large, the panel collapses to a toggle tab or a narrow layout.
- Creative inventory: the storage panel only, with no crafting, since that screen has no crafting grid.

### 3.2 Recipe book integration
- Uses the vanilla recipe book on the left side unchanged, including its tabs and its "show craftable only" filter.
- Craftability counts **inventory plus storage within the radius**. Like vanilla's inventory counting, enchanted, damaged and renamed items in storage are not counted as ingredients.
- Recipe states:
  1. **Craftable:** enough ingredients are reachable now. Vanilla style.
  2. **Not craftable:** not enough ingredients anywhere. Vanilla style.
  3. **Out of reach** (client-only mode only): enough ingredients are known in storage, but some are in chests beyond reach. Shown with a distinct tint and a tooltip.
- The 2x2 inventory grid only offers recipes that fit in 2x2, which is vanilla behaviour.

### 3.3 Crafting
- Clicking a recipe crafts **one**. Shift-clicking crafts **as many as possible**, as in vanilla: one grid-full, capped by the ingredients' stack sizes.
- Ingredients are pulled from storage, placed in the grid through vanilla's recipe placement, and the result goes to the **player inventory**. The client setting `craftToInventory` (default on) can turn the last step off, leaving the recipe in the grid like vanilla.
- **Inventory full:** the craft stops early and shows a message. Nothing is ever dropped. Leftover grid ingredients go back to the inventory, then to storage. If the pulled ingredients themselves wouldn't fit, a shift-click crafts fewer, and a single click refuses with a message.
- Inventory items are used first, then the nearest chests. This order is configurable.
- v1 does only **direct crafts**, meaning recipes whose ingredients already exist. See phase 6 for multi-step crafting.

### 3.4 Taking and putting away (phase 5, planned Nov 6)
Move items between storage and the inventory from the storage panel, without opening chests.

- **Taking:** works like a chest. Left-clicking a tile puts a stack on the cursor, right-clicking puts half on the cursor, and Shift-clicking moves a stack straight into the inventory. There's no setting for this. (Nov 9: right-click no longer takes half; it opens the container or takes one, and Shift-right-click shows where or takes all that fits, both settings. See 8a, "Panel controls".) Clicking the tile of the item you're already holding takes more of it, into the inventory, so rapid clicks keep taking; clicking anywhere else on the panel while holding something puts it away. An item a running take is bringing to the cursor counts as held. (Nov 6.)
- **Holding still while clicking:** while a background job runs or waits, and for 1.5 seconds after any panel or recipe click, the panel's tiles keep their order and the recipe book doesn't recount; recipe book updates from newly unlocked recipes wait until the hold ends too. Counts update in place, a tile that runs out stays as an empty placeholder, and new tiles go at the end; everything re-sorts once the hold ends. A new search always re-sorts. This keeps rapid clicks landing on the same tile or recipe. (Nov 6.)
- **Locating** moves off the plain click, which now takes: middle-click or Alt-click a tile to highlight its containers (3.1). In client-only mode, a click on an item held only in containers beyond reach highlights them instead of taking.
- **Putting away:** dropping the cursor stack onto the panel stores it; right-click stores one item. While the panel shows, shift-clicking a main-inventory stack (hotbar or the rows above it) stores the whole stack, like shift-clicking into a chest. Vanilla treats shift with either mouse button the same, so `putAway.shiftClick` picks which button stores (`left` by default, or `right`, or `off`), and the other keeps vanilla's shift-click. (Added Nov 6.)
- **Stacking:** stored items fill matching partial stacks first, across both halves of a double chest, then empty slots, the way a shift-click does. Items only go into chests, barrels and shulker boxes. Hoppers would pass the item on, and dispensers could fire it.
- **Where it goes**, like a copper golem would sort it:
  1. The nearest container that already holds the same item type and has room. This matches by item type, ignoring enchantments and other components, so a new enchanted book joins the chest of enchanted books. Copper chests were skipped in this step as a golem's inbox; since Nov 8 they count like any other container, so storage built from copper and regular chests both works (the `copper_chest` fallback below still applies to items no container holds).
  2. If there's none, it depends on `putAway.fallback`:
     - `copper_chest` (default): the nearest copper chest with room, so a copper golem can carry the item to the right place. If there's no copper chest with room, it uses `nearest`.
     - `nearest`: the nearest container with room.
     - `empty`: the nearest empty container, then `nearest`.
  3. If nothing has room, it stays in the inventory or on the cursor, with a message. Nothing is ever dropped.
- **Server mode:** new payloads for take (item, amount, to cursor or inventory) and put away (amount from the cursor). The server moves items directly within the radius and can set the cursor itself.
- **Implementation notes (Nov 6):**
  - The storage screen (keybind) has no cursor, so there a click takes a stack into the inventory (and since Nov 9 "Take one" takes one into it). Putting away works from the inventory and crafting table screens.
  - Taking matches by tile. The first matching stack decides the exact item, and only stacks that stack with it are taken (worn copies of a tool don't stack, so you get one).
  - Server mode uses `take` and `put_away` payloads (protocol version 3; `put_away` names the cursor or an inventory slot). The server stores with its own insert that fills partial stacks first; vanilla's hopper insert fills whichever slot comes first.
  - In client-only mode, an item parked in an inventory slot on its way to or from the cursor isn't drawn in that slot; it's drawn on the cursor until it really gets there. The server config has `allowTakeAndPutAway` (default true), sent in `hello`.
  - Nov 7: where items can't be moved (`allowTakeAndPutAway` off, or client-only mode with memory off), the panel only finds things: any click on a tile shows where it is, the tile tooltip says "Click: show where" in place of "Hold Ctrl for controls", and a held stack gets no put-away hint (a click with it on a tile shows where that tile's item is). Shift-clicks, drags and the scroll wheel keep their vanilla behaviour.
  - Client-only taking onto the cursor (a stack, or one since Nov 9) and putting away each need one free inventory slot to hold the item between menus. Put-away of one item picks up the held stack in the container, right-clicks one item into the target slot, and puts the rest back.
  - Client-only put-away only knows remembered containers, so a container you've never opened isn't a target. Room is estimated from memory and confirmed when the container opens.
  - Phase 4's crafting session became a general background-job runner (`client/background/BackgroundJobs`), used by crafting, taking and putting away.
- **Client-only mode:** uses the background container access from phase 4, so it only reaches containers within the player's reach. Put-away picks the target from memory, then checks the real contents when the container opens, moving on to the next candidate if the memory was out of date. Taking onto the cursor goes into a free inventory slot first, then the mod picks it up. Before any container opens, the mod checks that the inventory has room, because vanilla drops a cursor item if a container closes with no space left. The same limits as phase 4 apply: lid animation and sound for other players, sculk sensors, one round trip per container, and packet pacing.

### 3.6 Multi-step crafting (phase 7, planned and implemented Nov 6)
Decided with the user Nov 6: via-intermediates recipes look craftable with a blue tint, spare intermediates stay in the inventory, and shift-click crafts as many as possible.
- **What it does:** a recipe whose ingredients aren't all there, but can be made from what is there with other unlocked crafting recipes, is *craftable via intermediates*, a third recipe book state. Clicking it crafts the intermediates first, then the recipe. Example: oak logs in a chest, nothing else, and a click on the wooden pickaxe crafts planks, then sticks, then the pickaxe.
- **Which recipes:** only unlocked crafting recipes (the player's recipe book) that fit the grid in use: 2x2 in the inventory, 3x3 at a crafting table. Any of them can be an intermediate, including unpacking storage blocks (iron block → ingots) and packing (ingots → block). Never a recipe that turns something back into an item already on the chain, so there are no loops. Up to 4 levels of intermediates and 12 steps. Smelting, stonecutting and other stations aren't used.
- **Planning:** inventory, grid and storage (the radius in server mode, only containers within reach in client-only mode, as in phase 4), with the same rules as direct crafting: enchanted, damaged and renamed items don't count. For each ingredient, what's already there is used first, and the rest is crafted, picking the recipe whose ingredients there are most of (oak planks if oak logs are the most plentiful). Each intermediate is crafted exactly as often as needed; spare output, such as a fourth plank, stays in the inventory. A recipe that's craftable directly is crafted directly, as now.
- **Click and shift-click:** a click crafts one. Shift-click crafts as many as possible, as vanilla would with the ingredients there (at most one grid-full), with exactly the intermediates for that many.
- **Recipe book:** via-intermediates recipes count as craftable, so they show with "show craftable only", and get a blue tint. The tooltip lists what's crafted first, such as "Crafts first: 2 Oak Planks, 1 Stick". In client-only mode, a recipe that needs storage out of reach for its intermediates gets the out-of-reach state, as now.
- **Server mode:** the client plans from the live data and sends `craft_request` with the steps (recipe and how many times); protocol version 5. The server checks each step (unlocked, a crafting recipe, fits the grid), pulls its ingredients from storage, places it like vanilla once per craft, and shift-clicks the result into the inventory. Then comes the final recipe, as now. If a step can't be done because storage changed, the chain stops with a message, and what was crafted so far stays in the inventory.
- **Client-only mode:** one background job. It pulls all the base ingredients from containers within reach (each container visited once, as now), then at the grid, for each step, sends place-recipe once per craft, shift-clicks the result, and waits until the grid is empty (the server crafts every set). Then the final recipe, as now. Each step adds about one round trip and the verify wait (3.3, 4.2).
- **Setting:** `craftIntermediates` (default on), on the main settings page.
- **Implementation notes (Nov 6):**
  - One planner for both modes, on the client (`client/recipe/CraftChains`), built from the recipe book: each unlocked entry's per-slot ingredients, result and shape. The recipe index is rebuilt when the recipe book changes. Before searching, it works out which items can be had at all within each number of levels, ignoring amounts, so hopeless branches are skipped; a search also stops after 1,500 recipe tries.
  - For each recipe's ingredients, what's there is reserved for all of them first, then the rest is crafted, so crafting one ingredient doesn't use up what another needed as it was. Spare intermediates from earlier steps are used before starting items.
  - Slots that take the same items are one need: a pickaxe's three iron ingot slots need 3 ingots, so one iron block (9 ingots) covers them, and before crafting more of something, the spare from crafts already planned is used. (Nov 6, after the first in-game test: each slot was planned on its own, so an iron pickaxe from iron blocks crafted 3 blocks into ingots and sticks twice.) The tooltip adds up what each item's steps make.
  - An intermediate never uses up an item that's being made further up its chain, the clicked recipe's result included. (Nov 7, after the second in-game test: crafting an iron block with too few ingots unpacked an iron block from storage into ingots to pack them back into a block.)
  - The recipe book check runs on every recount, for each recipe the grid can show that isn't craftable directly. `debug.log` says how long it took ("Checked N recipes for intermediates in X ms").
  - Server mode: `craft_request` carries up to 12 steps (protocol 5). The server crafts each step a grid-full at a time, placing once per craft and shift-clicking the result, and then the clicked recipe as before. Leftovers in the grid go to the inventory, then storage.
  - Client-only mode: the craft job's finish phase runs the steps. For each grid-full, it sends place-recipe once per craft, waits until the grid holds them, shift-clicks the result, and waits until the result slot is empty (the server crafted every set); the progress line says "Crafting intermediates: step N of M".
  - Settings: the container toggles moved to their own "Containers..." page, so the main page has room for "Craft intermediates" (and phase 8's "Mouse..." page later) at large GUI scales.

### 3.5 Mouse shortcuts and other inventory mods (phase 8, planned Nov 6, implemented Nov 7)
Goal: the scroll wheel and shift-drag from Mouse Tweaks and Inventory Profiles Next (IPN) work on storage, and those mods keep working next to the panel. None of them becomes a requirement.

- **Why the mod does it itself:** Mouse Tweaks and IPN work on a menu's real slots, by sending the clicks a player would. The panel isn't slots: it shows containers that aren't open, so there's nothing for them to click, and neither has an API for storage like this (Mouse Tweaks' API is for mod screens with unusual slots; IPN publishes none). So the panel gets its own scroll and drag, made to feel like Mouse Tweaks', and the mod makes those mods' clicks on inventory slots do the right thing while the panel shows.
- **Status of the mods (Nov 6):** Mouse Tweaks 2.31 and IPN 2.3.x have 26.2 Fabric builds. More Mouse Tweaks (Mouse Wheelie's features as a Mouse Tweaks add-on: Ctrl-click to quick-move matching stacks, Alt-click to drop, recipe book quick-crafting) only goes up to 1.21.8, so it's covered once it's updated.

**Scroll wheel** (like Mouse Tweaks' wheel tweak, with storage as the other inventory; decided Nov 6):
- One rule everywhere: **scroll down takes from storage into the inventory, scroll up puts away into storage**, one item per notch, whether the mouse is over an inventory stack or a panel tile. (The user's habit from Mouse Tweaks.)
- Over an inventory stack (hotbar or the rows above) while the panel shows:
  - Down: one more of that exact item, into that stack first; once it's full, into other stacks of it, then an empty slot, like a take. Nothing happens if storage has none.
  - Up: one item from that stack is put away by the usual rules (3.4).
- Over a panel tile (inventory screen, crafting table, and the storage screen, which has no inventory slots):
  - Down: one of the tile's item into the inventory, as a take of one.
  - Up: one of that item from the inventory is put away, taken from the smallest matching stack, the rows above the hotbar first, so full stacks and the hotbar stay as they are. Nothing happens if the inventory has none.
- The grid then scrolls with Shift+scroll anywhere on the panel, or plain scrolling over the scrollbar, the search box, the footer or empty slots. Shift+wheel arrives as sideways scrolling on some systems (macOS), so either axis counts while Shift is held.
- The wheel never touches the cursor stack.
- While the panel shows, this replaces Mouse Tweaks' wheel tweak over inventory slots (in the inventory screen, Mouse Tweaks would move items between the hotbar and the rows above). With the panel hidden, or in any other screen, Mouse Tweaks works as usual.
- Each notch counts as a click for holding still (3.4).
- Server mode: instant. `take` gets an exact amount and an optional target inventory slot, so the protocol version goes up; `put_away` already has "one" for an inventory slot. Client-only mode: notches in a row on the same stack or tile in the same direction join one queued job, so a fast scroll of ten opens each container once instead of ten times; the exact amount uses phase 4's one-at-a-time right-clicks into the target slot.

**Shift-drag** (like Mouse Tweaks' left-drag with Shift):
- Over inventory stacks: with the panel showing, a shift-drag with the put-away button (`putAway.shiftClick`) puts away each stack it passes over, once per stack.
- Over panel tiles: a shift-drag takes a stack of each tile it passes over into the inventory, like shift-clicking each. A drag that starts on the panel stays a tile drag, and one that starts on inventory stacks stays an inventory drag.
- One rule underneath: every quick-move of a main-inventory stack made through the screen (`slotClicked` with QUICK_MOVE and the put-away button) becomes a put-away while the panel shows. It replaces today's check on the mouse press, and also covers vanilla's shift-double-click (which then puts away every stack of that item), Mouse Tweaks' shift-drag (it quick-moves each slot it passes) and More Mouse Tweaks' Ctrl-click of matching stacks, if that goes through the screen too. The mod's own drag over inventory stacks runs as well, and the two never store a stack twice (implementation notes below).

**Living with the other mods:**
- **Safety first:** while a background container is open (phases 4–6), the screen's own menu is closed on the server, so a click from another mod (an IPN auto-refill, a Mouse Tweaks drag that started before the job) would land in the hidden container with the wrong slot numbers. Every container click that isn't the mod's own is dropped while a hidden container is open (a flag around `Parking.click`, checked in `MultiPlayerGameMode.handleContainerInput`). This protects the existing jobs as well, so it's worth doing first.
- **Mouse Tweaks' wheel tweak** in the inventory moves items between the hotbar and the rows above. With the panel showing, the mod's scroll has to get the event first and consume it. Whether Fabric's scroll event runs before Mouse Tweaks' hook needs checking; if it doesn't, a soft mixin (`@Pseudo`) into Mouse Tweaks.
- **IPN locked slots** must never be put away by shift-click, drag or scroll. IPN has no public API, so this needs a look at how it keeps its locks (an optional, guarded lookup). IPN's sort buttons sit at the inventory's top right; check they don't overlap the panel toggle. Its item scrolling only works with a container open, so the inventory screen isn't affected.
- **Keys:** while a job runs, screens ignore keys except Escape; IPN's sort hotkey may go around that, so check it.
- **Detecting the mods:** `FabricLoader.isModLoaded` with the mod IDs from the jars (expected `mousetweaks`, `inventoryprofilesnext`, `moremousetweaks`). For testing, they go in as runtime-only dependencies so `runClient` loads them (IPN also needs Fabric Language Kotlin and libIPN).

**Implementation notes (Nov 7):**
- Mouse Tweaks on Fabric (`mousetweaks`, read from its source) gets its input from Fabric's screen events and does its wheel tweak in the after-scroll event. The mod takes a scroll in the allow-scroll event and consumes it, so over the panel and inventory stacks Mouse Tweaks never also acts on it. Its shift-drag quick-moves each slot through the screen's `slotClicked`, which is where the mod turns quick-moves into put-away (`AbstractContainerScreenMixin`), so that works without any special case. The mod's own drag over inventory stacks runs too, for whichever button stores; both share one record of the stacks this drag has stored, so none is stored twice. (Nov 7: at first the mod's drag was off while Mouse Tweaks was loaded, but Mouse Tweaks' shift-drag only uses the left button, so "Store with: Shift+Right" had no drag at all.)
- The click guard is in `MultiPlayerGameModeMixin` (every container click passes `handleContainerInput`). `Parking.click` marks the mod's own clicks. While a job from a screen runs, other clicks are dropped; during the stacked-cart scan, only while a cart is open on the server.
- Server mode: takes and put-aways go through a client outbox, one per tick, and scroll notches on the same target in a row merge into one request. The server takes up to 4 such requests per player per tick (was 1). Protocol 6: `take` has an exact-item flag, an amount and a target slot; `put_away` has an amount instead of "one".
- Client-only mode: a counted take picks up a matching stack in the container, right-clicks one item at a time into the target slot (or wherever there's room), and puts the rest back, all in one tick, across containers until the amount is reached. A counted put-away does the same the other way. Waiting requests for the same target absorb new notches.
- Mouse Tweaks and IPN are optional and not in the dev setup; to test with them, drop their 26.2 Fabric jars (IPN also needs Fabric Language Kotlin and libIPN) into `run/mods`. Not done yet: keeping IPN's locked slots out of put-away, and checking IPN's buttons and sort key next to the panel, which need IPN installed.
- Shift-double-click is recognised by the mod itself: a second shift-click on the same slot within 300 ms (vanilla's window is 250) stores every main-inventory stack of the item the first click stored, and vanilla's own clicks for that double-click are swallowed. Vanilla works it out from what the slot holds on the second click, but by then the server has often emptied it, so vanilla's version did nothing. (Nov 7, after the first in-game test.)
- First in-game test (Nov 7): scrolling worked, also with Mouse Tweaks installed. With IPN, a few things broke or didn't work quite right; the user set that aside for now.
- IPN retest (Nov 8, IPN 2.3.8 with libIPN 6.9.0):
  - IPN's sort button sits slightly over the panel toggle. Left as is: IPN lets players move its buttons.
  - Scrolling works with IPN as long as "Scroll inventory" is on (it was off in the first test). libIPN does hook `MouseHandler.onScroll` at its head and can cancel there, before any screen sees the scroll, so if IPN's own scrolling ever takes over, that's where to look.
  - IPN's swipe moving and the put-away shift-drag both acted on the same drag: some stacks went to storage, others were quick-moved within the inventory. IPN's swipe sends its quick-moves straight to `MultiPlayerGameMode.handleContainerInput`, past the screen, so `routeQuickMove` never saw them. Now, while a put-away drag runs, such a quick-move on a main-inventory stack of the screen's menu is stored instead (`PanelHooks.routeDraggedQuickMove`, sharing the drag's record so each stack is stored once). Clicks made through the screen are marked as already decided, and the mod's own clicks pass untouched.
  - In client-only mode, a shift-drag over tiles (taking) made IPN's "highlight focused items" squares appear in random places: IPN places them by the player's open menu, which during a job is the hidden container's. `IpnSlotHighlightMixin` (a `@Pseudo` mixin on IPN's `SlotHighlightHandler`, applied only when IPN is installed, `require = 0`) skips IPN's highlight drawing while the open menu isn't the screen's. After the next test it covers all three of IPN's slot overlays, which all draw by the open menu: `SlotHighlightHandler` (green squares), `AutoRefillHandler` (purple arrows) and `LockSlotsHandler` (the yellow highlight while Alt is held), at their `on…Render` and `draw…` methods. Holding off only while a hidden container was open made them flash between containers, so they now hold off while a job runs or waits in the queue (`BackgroundJobs.hidesSlotOverlays`).
  - Locked slots (Nov 8): a stack in a slot IPN has locked is never put away, by shift-click, shift-double-click, either drag, the scroll wheel over it or over its tile. In server mode put-away goes to the server as a request, past IPN's own guard on clicks, so this was a real hole. `IpnLockedSlots` asks IPN's `LockSlotsHandler.isSlotLocked(int)` by name (IPN numbers slots as vanilla's inventory does); a shift-click on a locked stack goes on to vanilla's quick-move, which IPN guards itself. Client-only jobs never park items in or count items into a locked slot either (`Parking.emptySlot`, `Parking.roomFor`, `CraftJob.inventoryTarget`), since IPN may stop clicks there and strand the item on a hidden cursor. After the user's test, nothing taken from storage lands in a locked slot either: vanilla's quick-move and the server's inventory fill both use the first empty slot. Client-only, while any slot is locked, a whole-stack take goes by hand to allowed slots (`Parking.quickMoveOut`) instead of a shift-click; server mode, take and craft requests carry the locked slots as a bit mask (protocol 8), and the server fills around them (`server/LockedSlots`) when taking, pulling ingredients, checking they fit and returning grid leftovers. Still vanilla's: crafted results shift-clicked out of the grid, and ingredients the recipe book places from the inventory.
  - IPN's actions (Nov 8): sorting (key and buttons), move matching, throwing and IPN's scroll wheel work out a run of clicks from the player's open menu. While a client-only job runs that's a hidden container (IPN would sort the chest being read), and the click guard drops most of the clicks, so a sort stopped halfway. `IpnActionsMixin` (`@Pseudo` on IPN's `GeneralInventoryActions`) makes them wait while a job runs or is queued, a hidden container is open, or put-away and take requests wait for the server; sort, move and throw say "Wait until storage is done".

**Settings** (the "Mouse..." page in the in-game settings):
- `mouse.scrollDirection`: `down_takes` (default: down takes from storage, up puts away) or `up_takes`.
- `mouse.scrollOverInventory` (default on): scrolling over inventory stacks moves items while the panel shows. Off leaves the wheel there to vanilla and Mouse Tweaks.
- `mouse.scrollOverTiles` (default on): scrolling over tiles moves items. Off: plain scrolling scrolls the grid again, as before phase 8.
- `mouse.shiftDrag` (default on): shift-dragging over inventory stacks or tiles (above).
- Tile tooltips say which way the wheel takes and puts away.
- The tile tooltip is kept short (Nov 7: it had grown big enough to cover half the inventory): the item's own tooltip, "Total: N · Inventory: N", "Storage: N in N containers · seen … ago", and "Hold Ctrl for controls". The control hints (click, shift-click, scroll, locate) show only while Ctrl is held.

## 4. Operating modes

### 4.1 Server mode (server has the mod, or singleplayer)
- The client and server do a handshake through a custom payload to detect the mode. The server sends `hello` (protocol version, `maxRadius`, `allowCrafting`) to clients that registered the channel. A client on a different protocol version stays in client-only mode. (Implemented Nov 6.)
- **Live data:** the client subscribes with its radius and container kinds. The server rescans every 10 ticks (0.5 s) and sends only containers whose contents changed, plus removals, split into batches of 64 containers. Totals are always accurate, with nothing stale, and the panel footer says "live". Only loaded chunks are scanned. Unopened loot chests are skipped, because reading them would generate their loot. Locked containers are skipped when `respectContainerLocks` is on, even if the player holds the key (stricter than vanilla). The client keeps recording memory in this mode, but doesn't use it.
- **Crafting:** recipe book clicks in the inventory and crafting table send `craft_request(containerId, recipe, flags, radius, kinds)` in place of vanilla's place-recipe packet. The flags are shift-click, `craftToInventory`, and `ingredientSourceOrder`. The server:
  1. makes vanilla's checks (open menu, recipe unlocked, placeable), at most one request per player per tick;
  2. limits the radius to the server's `maxRadius` and scans containers as for live data, nearest first;
  3. works out the ingredients with vanilla's solver over inventory, grid and storage, then moves only the missing ones into the player inventory, all or nothing, after checking they fit;
  4. runs vanilla recipe placement, then with `craftToInventory` shift-clicks the result like a player would (so vanilla handles stats, advancements and container items like buckets).
- Everything happens instantly and server-side. There are no visible chest openings and no desync. The recipe book shows no "out of reach" state in this mode.

### 4.2 Client-only mode (server without the mod)
- **Memory:** contents are recorded every time any container is opened, by hand or in the background. Records are kept per server or world and per dimension, keyed by block position, with a double chest stored as one entry. Totals for chests out of reach come from this memory and may be out of date. The panel shows a "last seen" age.
- **Reach:** uses the player's actual `block_interaction_range` attribute, not a hardcoded 4.5. If a server raises it, the mod automatically reaches further.
- **Background crafting flow:**
  1. Plan which reachable containers to pull from.
  2. For each container: send the vanilla "use block" packet, then intercept the server's open-screen response. The chest screen is never shown; the current screen stays visible. Quick-move the needed stacks to the inventory, then send close-container.
  3. If at a crafting table: opening a chest closes the table on the server, so the mod reopens the table with another "use block" packet after pulling everything. The 2x2 inventory grid isn't affected, because the server always has the player inventory open.
  4. Send vanilla place-recipe and take the result.
  5. Verify the inventory matches what was expected. If not, stop and resync.
- **What the player sees:** the inventory or crafting screen stays open with a small progress indicator. No chest GUIs flash on screen.
- **What can't be hidden:**
  - Chest, barrel and shulker lids still open and close in the world, and their sounds still play for **other players**. The mod can mute and hide these locally for you only.
  - Opening a container triggers vibration, so **sculk sensors nearby will activate**.
  - Speed: about one network round-trip per container, plus one to reopen the table. Example: 3 chests at 80 ms ping is about 0.3 s.
- **Failure handling:** if the server refuses an interaction (out of range, a protection plugin, a timeout), the craft stops cleanly and shows the reason.
- Uses configurable packet pacing to avoid tripping anticheat.
- **Implementation notes (phase 4, Nov 6):**
  - Planning uses memory and the same rules as server mode, but only containers within reach. If the recipe is craftable only with storage out of reach, the click shows a message and falls back to vanilla's ghost recipe.
  - Each container opens with a normal right-click. The open-screen reply is turned into a menu with no screen, and the needed stacks are shift-clicked into the inventory, one per step, using the real contents (memory may be out of date). When a stack is bigger than what's still needed and 16 or fewer are needed, the mod takes exactly that many: it picks up the stack, right-clicks the items one at a time into an inventory slot, and puts the rest back, all in one tick so nothing can interrupt while the container's cursor holds the stack. A single craft never needs more than 9 of one item, so it takes exactly what it uses. Larger needs (shift-click crafts) shift-click whole stacks, which can pull up to a stack extra; extra items stay in the inventory. Server mode always takes exact counts. (Exact amounts added Nov 6.) Contents are recorded to memory while the container is open.
  - The crafting table is reopened from the position you opened it at, which must still be within reach. The mod ignores the server's close of the table so its screen stays up meanwhile. When the table reopens, the new menu goes into the screen that's already showing, so the recipe book's tab, page and layout, and the storage panel, carry on without a new screen. If that doesn't work out (another screen showing), vanilla's new screen is used. (In place since Nov 6.)
  - The craft refuses to start, with a message, while sneaking (a right-click would use the held item), with an item on the cursor, or at a crafting table whose grid wouldn't fit back in the inventory.
  - While it runs, a progress line shows above the screen. Clicks on the recipe book and the storage panel are queued (up to 64) and planned when their turn comes, so each sees what earlier jobs changed; the progress line shows how many are waiting. Other clicks are ignored, because the screen's own menu may be closed on the server. Escape cancels the job and clears the queue, and so does any failure; a container still opening is then closed unseen. A queued take onto the cursor that finds the cursor already holding something goes into the inventory instead. (Queue added Nov 6.)
  - **Speed** (`clientOnly.speed`): at `normal`, the job does one step per tick with a `packetDelayMs` (50 ms) pause after each action, and verifies a craft after at least 300 ms (or 3× ping). At `fast`, there are no pauses: it runs steps until it has to wait for the server's reply (a container opening, the crafted result), and verifies after 100 ms (or 2× ping). Vanilla servers don't limit click or interaction rates unless `rate-limit` is set in `server.properties`, but anti-cheat plugins may flag fast mode.
  - Verifying: after taking the result, the mod waits for the server (at least 300 ms, or 3× ping) and checks that the result arrived.
  - With `craftToInventory` on, client-only mode also crafts inventory-only recipes straight into the inventory, as server mode does.
  - `muteOwnContainerSounds` and `hideOwnContainerAnimations` hide sounds and chest/shulker lid events at those containers for you only. A barrel's open texture is a block state change and can't be hidden.

## 5. Storage scope

- Storage is the containers within a **radius around the player**, measured as a **cube**, so storage above and below counts too.
- Default radius: **32** blocks. It can be changed in the config screen and in the config file.
- The server has its own `maxRadius` cap that limits what any client can request.
- Supported containers in v1: chests (including double chests), trapped chests, barrels, shulker boxes (when placed), and hoppers, droppers and dispensers (configurable). Phase 6 adds chest minecarts, chest boats and hopper minecarts (5.1). Ender chest: later (9).
- **Shulker boxes stored as items** inside containers count as one shulker box item each. Their contents are **not** counted and not used for crafting. (Decided Nov 5.)

### 5.1 Chest minecarts and chest boats (phase 6, planned and implemented Nov 6)
- **What counts:** minecarts with chests and boats with chests (27 slots each) count as storage. Hopper minecarts count as a source, like hoppers, but never as a put-away target, because they move items on. Unopened loot minecarts (from mineshafts) are skipped, like loot chests.
- **Container key:** a container is identified by a block position *or* an entity UUID with its last known position. This changes the memory file (format v3) and the network protocol (version 4). Distance and the radius use the entity's current position when the client knows it, otherwise the last known one.
- **Server mode:** the server finds carts within the cube with one entity query. They're ordinary containers, so crafting, taking and putting away work on them unchanged.
- **Client-only memory:** a cart is recorded when you open it, keyed by its UUID. The client knows about every minecart within its tracking range (about 80 blocks). If you're near a cart's last known position and it isn't there, the memory forgets it or updates its position.
- **Highlights** follow a cart as it moves. The slot highlight works as for chests.
- **Stacked carts** (several carts in one space) share a hitbox, so in vanilla you can't choose which one opens.
  - In server mode, the server reads every cart in the stack directly, so all of them count.
  - In client-only mode, an interact packet names a specific entity, so the background access from phase 4 can open each cart in turn, regardless of the crosshair. When you open one cart by hand, the mod opens the rest in the background to record them. This is limited to the entity interaction range (3 blocks by default) and uses phase 4's pacing. It has its own on/off setting, because strict anti-cheat plugins may flag interacting with entities you aren't looking at.
  - The panel counts each cart as its own container. The highlight draws one outline for the stack with a "×N" label.
- **Implementation notes (Nov 6):**
  - Three new container kinds, each with its own toggle under "Containers to include": `chest_minecart`, `chest_boat` (bamboo chest rafts included) and `hopper_minecart`. Config files from before phase 6 get them switched on once (`configVersion`).
  - The shared key is `storage/ContainerKey` (block position or UUID). Server mode sends it in `storage_update` (protocol version 4); a cart's block is part of its content hash, so the client hears when it moves.
  - Memory file v3: a cart entry has `"entity": "<uuid>"`, and `"pos"` is the block it was last seen in. v1 and v2 files still load.
  - Recording: a right-click on a cart is matched to the next container screen, as for blocks. Opening a ridden chest boat with the inventory key is recorded too.
  - Forgetting: while the client has a remembered cart loaded, its position follows the cart. A cart that isn't loaded while you're within 16 blocks (horizontally) of where it was last seen, and at least 5 seconds after joining or changing dimension, is forgotten after two checks in a row (about 4 seconds), so a short delay in entities arriving doesn't drop it.
  - Background access sends the interact packet itself, naming the entity and aimed at the middle of its box. Reach for carts is the entity interaction range with no extra: the server allows 3 blocks more, but anti-cheat plugins check much closer. `clientOnly.extraCartReach` ("Extra cart reach", default off, with a warning in its tooltip) adds 2.5 blocks, leaving half a block of the server's allowance for movement and lag. It applies wherever carts are reached: jobs, the stack scan and the recipe book's "out of reach" state. (Added Nov 6, after the first in-game test.)
  - `clientOnly.extraBlockReach` ("Extra block reach", default off, same warning) does the same for blocks: off, containers (and the crafting table that's reopened) must be within the crosshair's block reach (4.5 blocks by default); on, 1 block more, which is all the server accepts. Until Nov 6 blocks always used that extra block; the default changed to crosshair reach, to match carts and keep clear of anti-cheat plugins. (Added Nov 6, after the second in-game test.) A chest boat only opens its chest for a sneaking click (otherwise you get in), and the server takes the sneak flag from the interact packet, so the mod sends your real input again right after. Sneaking therefore doesn't stop a job that only opens carts; jobs that open blocks, or reopen a crafting table, still refuse while sneaking.
  - What a stack is: two carts or boats are stacked when their boxes overlap sideways (more than just touching, so a train of carts end to end isn't a stack) and overlap or touch up and down. That covers carts squeezed onto one rail, partly or fully, and carts resting on top of each other. A stack is everything linked this way, so with three partly overlapping carts the two outer ones count even if they don't overlap each other. (Nov 6: the first version only counted carts within half a block of the opened one, which missed the far cart of a partly overlapping stack of three.)
  - Stacked carts: `clientOnly.scanStackedCarts` (default on, "Scan stacked carts" on the client-only page). When you close a cart you opened by hand, the rest of its stack within reach is opened one by one, with phase 4's pacing, and recorded. If the scan stops early, the game log says why ("Stopped reading stacked carts").
  - The scan belongs to no screen: opening the inventory while it runs doesn't stop it, and its progress line shows above the inventory. Each cart is closed as soon as its contents arrive, because closing any container screen closes whatever menu is open, which would otherwise close a cart under the scan. (Nov 6, after the second in-game test: the first version stopped whenever a screen opened, so checking the panel right after closing a cart cut the scan short at one of two carts. That was also the likely cause of "only ever 2" in the first test.) It shows no messages. Server mode doesn't need it.
  - The scan steps aside for the player (Nov 7, after a test with a stack of 14). The server lets a player have one container open at a time, so it can't run while you use a crafting table, but it doesn't block you either. A right-click, a click or key in the inventory, or a request from the panel or recipe book makes it stop before its next cart. The cart it was opening is still recorded, because its contents reach the client before whatever you opened replaces it. The rest waits until you've closed your container and haven't clicked for half a second, and is dropped after a minute. Clicks and keys only wait while a cart is open on the server right now (about one round trip). A cart only ever opens a 3-row chest menu (a hopper menu for hopper minecarts), so a container you open meanwhile is never taken for it.
  - Carts of the stack read in the last 5 minutes aren't read again. (This was the "Rescan stacks" setting, `clientOnly.stackRescanMinutes`, until Nov 7, when the user dropped it: hardly anyone would change it, and "Scan stacked carts" can still turn the scan off.) Carts only change when someone opens them or a hopper empties them, and the mod records every cart it opens, so rereading a stack you keep reopening mostly repeats what it knows.
  - Unopened loot carts can't be told apart on the client (it never sees loot tables), so client-only mode treats every cart the same; opening a loot cart generates its loot, as it would by hand.
  - Highlights are redrawn each tick from where the client has the cart; a cart it doesn't have is outlined at the block it was last seen in. Stacked carts, by the same rule as the scan, share one outline with a "×N" label. Opening one cart of a stack by hand removes only that cart from the count.
  - Opening a chest minecart or boat makes no sound and has no lid, so the "hide my container" options don't apply. Like vanilla, it still triggers sculk sensors and angers nearby piglins, in the background too.

## 7. Phases

0. **Project setup:** done Nov 5. The mod loads in `runClient`.
1. **Foundation:** container memory, the storage panel (search, totals, highlighting, show/hide toggle) on the inventory and crafting table, the keybind screen, and config.
2. **Recipe book:** counting storage toward craftability, including the "out of reach" state.
3. **Server mode:** handshake, live snapshots and server-side crafting. This makes crafting fully work in singleplayer and on your server.
4. **Client-only crafting:** the hidden background container access described in 4.2.
5. **Taking and putting away:** move items between storage and the inventory from the panel, with copper-golem-style sorting (3.4). The server-mode half only needs phase 3; the client-only half reuses phase 4's background access.
6. **Chest minecarts:** minecarts and boats with chests as storage (5.1). The server-mode half only needs phase 3; scanning stacked carts in client-only mode needs phase 4. Implemented Nov 6. First in-game test: everything worked except that a stack of three only recorded two carts. Second test: the scan found all three but was cancelled when the inventory opened; fixed. "Extra cart reach" and "Extra block reach" were added. Done and verified in-game Nov 6.
7. **Multi-step crafting:** a planner for intermediate items (logs → planks → sticks → pickaxe) that repeats vanilla recipe placement, using only unlocked recipes, with a third "craftable via intermediates" recipe state (3.6). Implemented Nov 6; verified in-game Nov 7 after two planner fixes.
8. **Mod compatibility (planned Nov 6):** scroll wheel and shift-drag on storage, and Mouse Tweaks, Inventory Profiles Next and (once updated) More Mouse Tweaks working next to the panel (3.5). Start with the click guard for hidden containers, which also protects phases 4–6. Implemented and verified in-game Nov 7, after fixes for shift-double-click, the tooltip size and right-button shift-drag. ## 8a. Review pass (Nov 7)
A read-through of the whole mod after phase 8, fixing what was clearly wrong without changing how it's used:
- **Memory:** an entry that can't be read is skipped instead of losing the whole file, and a file that couldn't be read in full is copied to `<file>.broken-<time>` before the next save rewrites it. A container recorded with the same contents as before (an open chest is recorded every half second) only updates "last seen", so the panel and recipe book don't recount. Each entry keeps its encoded JSON until it changes, so a save no longer re-encodes every remembered item.
- **Panel:** the sort works out each tile's name once instead of in every comparison (a big storage has thousands of tiles, recounted every second). An empty grid says why: nothing matches, no storage in range, remembering containers is off, or open containers to add them.
- **Highlights:** a container broken since the search loses its outline straight away.
- **Input:** when items can't be moved at all (the server turned taking and putting away off, or client-only mode with memory off), shift-click, shift-drag and the scroll wheel are left to vanilla and Mouse Tweaks instead of doing nothing.
- **Server mode:** recipe clicks go through the same paced outbox as takes, since the server handles one craft request per player per tick and dropped a second one. The `hello` payload reads the protocol version first and skips the rest on a mismatch, so a later change to it can't make an older client fail to read it and disconnect.
- **Leaving a world:** the intermediates planner's recipe index and the recipe book state are cleared, since they held on to the old world.

Then four additions the user picked (Nov 7):
- **Mod Menu:** Crafty Search's settings open from Mod Menu's mod list (`client/compat/ModMenuIntegration`, a `modmenu` entrypoint; Mod Menu is suggested, not required).
- **Panel sort:** a small button at the end of the search row cycles the order: most first (`#`, as before), by name (`A`), by mod (`@`). Ties break by name, then enchantment. The choice is saved (`panelSort`), and a new sort re-sorts at once, like a new search.
- **Remember the last search** (`rememberSearch`, default on, main settings page): a new panel, in the inventory, the crafting table or the storage screen, starts with the last search typed in any panel. Kept for the session.
- **Counts over highlights:** each outlined container shows how many of the item it holds, white above the outline; a stack of carts shows its total with "×N" under it. The counts are read again twice a second from live data (server mode) or memory, and a container that's run out loses its outline.

After the user's check (Nov 7): the panel is locate-only where items can't be moved (see 3.4), and the settings tooltips were cut down. The user then reworded them one by one (their wording is in `en_us.json`; some use line breaks, one line per state), dropped the tooltip on "Your inventory", and moved that button to the Containers page; "Remember search" moved up beside "Craft intermediates", freeing a row on the main page.

**Vanilla look (Nov 8).** The panel and its buttons are drawn to look like vanilla's own GUI, still with fills and vanilla's sprites, so the mod ships no textures (`GuiDraw`):
- The panel's background matches the inventory's pixel for pixel: corners cut away as vanilla's are (two pixels top left, three top right and bottom left, two bottom right), a two-pixel highlight and shadow with vanilla's inner corner pixels. The slots already matched.
- The scrollbar is the creative inventory's: a 14-pixel track sunk in like a slot, with vanilla's 12 by 15 thumb sprite (greyed out with nothing to scroll), and it can be dragged. The panel is 10 pixels wider for it (6 columns: 134). Clicking the scrollbar with an item held scrolls rather than putting the item away.
- Hovering a tile uses vanilla's slot highlight sprites (behind and in front of the item) instead of a white fill.
- The toggle button is drawn as the recipe book button is: its outline with cut corners, one-pixel highlight and shadow, light grey face, blue while hovered (only under the mouse, not while focused after a click), with a chest at full item size where that button has its book (scaled down to the face it looked small and lost its top). The sort button uses the same frame with a dark label.
- At the crafting table the toggle mirrors the recipe book button: level with it, as far from the right edge as that button is from the left, right of the result slot. (Below the book button it touched the "Inventory" label; above it was tried first.)

**Shulker box contents (Nov 8).** Setting `shulkerContents` ("In shulker boxes", Containers page, default on). A shulker box item carries its contents in its `container` data component, which live data and memory both keep, so the items inside boxes in storage (and in the inventory, when "Your inventory" counts) count on their tiles, and the containers holding those boxes are sources: highlighted, with the boxed items in the outline's count. The tooltip counts loose and boxed items each with their own containers: "Storage: N in M containers" for loose ones, "In shulker boxes: N in M containers" (or just "In shulker boxes: N" for boxes the player carries). Opening a container during a search also marks the shulker boxes in it that hold the item, not only loose stacks of it. Put-away ranks containers by what they hold (`storage/PutAwayMatch`, both sides, always, whatever the toggle): a loose item goes where it lies loose, then where a box holds it; a shulker box goes where boxes share an item with it, then where its items lie loose, then where any box is; then the "New items" fallback as before. Copper chests take part in these matches too. Also in server mode a double chest's halves are now in vanilla's order (the half with chest type RIGHT first, the top rows on screen), so put-away fills the top half first as a shift-click does; ordering them by block position put the bottom half first for some facings. Copper chest matching and the halves order verified in-game Nov 9.

**Batched put-away (Nov 9).** In server mode each stack was its own request, and the client sends at most one request a tick (the server takes 4 per player per tick and drops the rest), so a shift-double-click over a full inventory took nearly two seconds. `PutAwayPayload` now carries a list of slots (protocol 9), and the outbox merges whole-stack put-aways waiting to be sent into one request; the server finds the containers once and stores each slot in turn, ranking the targets afresh for each item. A shift-double-click now stores the first stack at once and the rest a tick later. Scroll notches on one slot still add up into one counted request. Client-only mode can't batch: it opens containers and clicks like a player. Takes the same way (Nov 9, protocol 10): `TakePayload` carries a list of items, and whole-stack takes into the inventory waiting to be sent (a shift-drag over tiles) merge into one request; the server finds the containers and the kept slots once and takes each item in turn, showing at most one message ("none left", "no space"). Takes onto the cursor stay one item each. Items are never taken out of a box: the recipe book and crafting count only loose items, and a take from a tile that's only in boxes takes the box lying loose in storage that holds the most of it instead, as that box's own tile would (clicks and shift-drag; the scroll wheel takes nothing there, being one item per notch). With no such box in storage it shows where. The user ruled out moving items in or out of boxes, and ender chests.

Also Nov 8: client-only takes by hand around locked slots fill in vanilla's quick-move order, the hotbar first from the right (`Parking.roomFor` and `CraftJob.inventoryTarget` go through the menu from its end); in menu order the rows above filled first.

**Highlight markers (Nov 8).** With a shader pack (Iris), highlights didn't show through walls: the outlines are vanilla's always-on-top gizmos, and a shader pack draws lines with its own shaders, which don't keep them on top. So the HUD, which shaders don't touch, can also show a marker at each outline's middle on screen: a small green square with the count under it ("×N" after it for a stack of carts). Far markers draw first, so near ones are on top; markers off screen or behind the camera aren't drawn. The position comes from the camera's view-projection matrix (view bobbing isn't in it, so markers don't bob with the world). Setting `highlightMarkers` ("Markers" on the main page): With shaders (default; asks Iris's API whether a shader pack is on, looked up by name so Iris stays optional, and false without Iris), Always, Off. The outlines are still drawn either way; while markers show, the outlines leave out their own count labels, which would only repeat them. Also Nov 8: the outline labels moved from above the container to its middle (the count centred, a stack's "×N" under it, the two lines centred together).

**Progress line (Nov 8).** The client-only progress line over the screen ("Taking from storage: container 1 of 2 (+3 queued)") blinked off between queued jobs: when one job ends, the next starts on the following tick, and nothing was running in between. The last line now stays up while the queue still holds work.

**Leave one (Nov 8).** Setting `keepOne` ("Leave one", main page, default off). Taking and crafting from storage leave one of each stackable item in every container, so the container still holds it: putting away sends that item back there instead of to the "New items" choice, and a copper golem keeps sorting it there. Unstackable items (tools, armour) are taken as usual, since one of them is the whole thing. The rule (`storage/KeepOne`, shared by both sides): each container (a double chest's two halves together) keeps one item per item type, from one slot, a stack usable for crafting when there is one, so crafting counts lose exactly one.
- Server mode: `TakePayload.KEEP_ONE` and `CraftRequestPayload.KEEP_ONE` (protocol version 7). The server works out the kept slots once per request (`server/KeptSlots`); a kept slot never goes below one. A take that finds only kept ones says "Only the one left in each container remains (Leave one is on)".
- Client-only mode: `TakeJob` and `CraftJob` work out the kept slots of each opened container the same way. A kept slot can't be shift-clicked (that moves the whole stack), so "all but one" is pick up, put one back, drop the rest in the inventory, and put back what didn't fit, in one tick. Containers holding only kept ones aren't opened.
- The recipe book's craftable counts, the intermediates planner and client-only planning use each remembered container's counts less the kept ones (`MemoryEntry.takeableCounts`), so a recipe that only kept items could make doesn't show as craftable. The panel's totals still count everything in storage.

**Claims (Nov 8).** Server mode reads and moves items straight from containers, so a claimed chest was open to anyone with the mod: shown in their panel, usable for crafting, takeable. Now `StorageScanner.scan` leaves out every container the player couldn't open by hand (`server/protection/Protection`), so it shows nowhere and can't be used. Checked: vanilla's spawn protection (non-operators) and world border (`ServerLevel.mayInteract`); Open Parties and Claims (`IChunkProtectionAPI.onBlockInteraction`/`onEntityInteraction`, as an empty-handed use, with no chat message since it runs for every container in range); Flan (`ClaimHandler.canInteract` with the open-container permission); and the Common Protection API (`CommonProtection.canInteractBlock`/`canInteractEntity`), which GOML and others answer through (Flan too when it's installed). A double chest needs both halves allowed. Each mod's check is its own class, loaded only when that mod is installed; the mods are compile-only dependencies, never bundled. If a claim mod's API throws (a changed version), access is refused where that check applies and the log says so once: no storage beats other players' storage. `respectClaims: false` in the server config turns all of this off. Client-only mode needs none of it, since there the server sees ordinary clicks, which claim mods already guard.

**Recipe viewers (Nov 8).** JEI and REI put their item list right of the inventory, where the storage panel is, so the two overlapped. The panel's area (`PanelHooks.panelArea`) is now a JEI extra area (global GUI handler, entrypoint `jei_mod_plugin`) and an REI exclusion zone on the inventory and crafting table (entrypoint `rei_client`), so the viewer's list moves aside. EMI has no 26.2 build yet. The user didn't like the look of JEI's list squeezed in beside the panel, so while the panel is open the inventory screen now moves left (`PanelHooks.shift`): the inventory, the recipe book (open or not) and the panel sit centred together, and the right side is free for the viewer. The shift is half the panel's width, no further than keeps the recipe book's spot on screen, and none if the panel wouldn't fit anyway; it comes from the screen size alone, so opening the recipe book doesn't change it. The recipe book and the screen's position are both worked out from the screen width, so `AbstractRecipeBookScreenMixin` hands them one narrower by twice the shift. Opening or closing the panel lays the screen out again on the next tick (not inside the click, which would rebuild the widgets while they're being gone through), and a just-opened panel stays hidden until then so it doesn't jump. Above or below the inventory was the other option, but at GUI scale 4 on 1080p there are only about 50 pixels there. Then (Nov 8) REI laid its list out from the inventory's right edge with the panel cut out of it, so its columns didn't line up with the panel's edge. Both viewers now take the inventory and the panel together as the screen's area: REI through a `DisplayBoundsProvider` (priority 10, above REI's own -10 for container screens), JEI through screen handlers for `InventoryScreen` and `CraftingScreen` (JEI uses the handler registered closest to the screen's class), so the list starts at the panel's right edge. The exclusion zone and extra area stay too. To try them in the dev client: `gradlew runClient -Pwith=jei` (or `rei`; also `opac`, `flan`, `cpa` for the claim mods; comma-separated). Modrinth's Maven picks any loader's file for a version number several loaders share, so JEI, mezzconfig and Forge Config API Port are pinned by Modrinth version id in `gradle.properties`.

**Panel controls (Nov 9).** The user found right-click taking half a stack not much use, so the panel's controls were rearranged (protocol 11):
- **Right-click** (`mouse.rightClick`, Mouse page, "Right-click", default Open) and **Shift-right-click** (`mouse.shiftRightClick`, "Shift-right", default Show where) each pick from the same four (`TileClick`; first built with two each, the user asked for all four on both):
  - Open: the nearest container holding the item, one with it loose before one with it in a shulker box.
  - Take one: onto the cursor, or one more onto a held stack of it (onto a full one, or a different item, it goes into the inventory). With Shift, and on the storage screen, into the inventory.
  - Show where.
  - Take all: as much as fits in the inventory (not just one stack).
  - A tile only inside shulker boxes takes its one box for either take. Holding an item, a right-click set to Open puts one away as anywhere else on the panel, since a container can't open with an item on the cursor. Where items can't be moved, every click shows where, except one set to Open.
- **Middle-click and Alt-click** always show where.
- **Ctrl+scroll** moves a stack per notch instead of one item: over a tile, takes a stack per notch, or puts away whole stacks of it (smallest first, a stack just sent isn't picked again for a second); over an inventory stack, takes a stack per notch into it first, or puts that stack away. Shift+scroll still scrolls the grid. A tile scrolled empty (with "Leave one" off) stays as a placeholder while the scrolling goes on, and more notches on it do nothing; they used to scroll the grid under the mouse. Scrolling the other way still puts it back.
- **Q / Ctrl+Q** (the drop key as bound) over a tile throws one, or a stack, straight from storage onto the ground in front of the player, as over an inventory slot. Both modes; "Leave one" and the kept ones are respected. A tile only in shulker boxes shows where instead (a box isn't thrown for it). Not while the search box has focus (it types there).
- **Opening, server mode:** `OpenContainerPayload` (container key, radius, kinds). The server finds it with the same scan as live data (radius, kinds, claims, locks), then opens the menu vanilla would (9×3 or 9×6 chest, shulker box, hopper, dispenser) on a wrapper container (`server/RemoteOpen`) that stays valid while the player is within the server's radius plus 4 blocks, instead of vanilla's few. The wrapper doesn't pass the open and close on, so the lid stays shut (vanilla's opener count would also find no player next to it and close it). Server setting `allowRemoteOpen` (default on, sent in `hello`); with it off, the client falls back to the client-only way.
- **Opening, client-only mode:** a plain right-click on the nearest one within reach (`BackgroundAccess.useBlock`/`useEntity`, the sneak trick for chest boats), refused while a background job runs; beyond reach it shows where with the "out of reach" message.
- Either way the panel highlights the item's containers first, so the opened one has its slots marked and the others stay outlined, and the recorder is told which container the next screen is (`ContainerRecorder.expectOpening`). Closing it goes back to the world, as closing any container does (the user's choice).
- **Server mode takes:** `TakePayload.HALF` is gone; new flags `ALL` and `DROP`. A counted take is no longer capped at one stack (Ctrl+scroll asks for several); onto the cursor it's capped at what the held stack has room for. Everything going into the inventory or onto the ground goes in stacks no bigger than the item allows, so unstackable items never share a slot.
- **Client-only takes:** `TakeJob` has modes: a stack, one (pick up, right-click one into the parking slot, put the rest back), all (a shift-click per step until the inventory is full or the containers run out), counted, and throw (`Parking.drop`: the whole slot with one throw click, one item per throw click, or for most of a big stack pick it up, put back what stays one at a time and throw the rest from outside the window). A counted take now drops a whole cursor stack into a slot when that's no more than wanted, instead of always one item at a time, so Ctrl+scroll isn't 64 clicks per stack.

**Repeated recipe clicks (Nov 9).** In client-only mode, rapid clicks on a recipe queued one job per click, each opening every container it needed again (and reopening the crafting table), so ten clicks took ten trips. Now plain clicks on the same recipe queued in a row are one request (`ClientCrafting.QueuedCraft`): the first click still starts at once, and the clicks made while it runs become one job. That job plans all of them together (`CraftPlanner.plan` with the number of clicks; as many as there's enough for, and fewer if the ingredients wouldn't fit), opens each container once, and takes exactly what they use. With "Craft into inventory" on, the clicked recipe is then crafted round by round, a grid-full at a time, the way intermediates are (one more step after them); off, it places as many sets as the clicks would, up to what the grid holds. Shift-clicks aren't merged. Exact amounts got cheaper too: a need of most of a stack puts back what stays one item at a time and drops the rest in at once, so there's no longer a limit of 16 above which whole stacks came out. Server mode needs none of this: the server crafts each click in the same tick it arrives, and requests go out one a tick, so rapid clicks keep up.

**After the user's look at that (Nov 9):**
- **Exact amounts always.** The `clientOnly.exactAmounts` toggle is gone: with repeated clicks merged and exact takes down to a few clicks, whole stacks no longer saved time, and the extra they left filled the inventory.
- **"Store with"** (`putAway.shiftClick`) is on the Mouse page; the main page's rows closed up behind it.
- **Batching takes and put-aways (client-only).** Server mode already merged them (protocols 9 and 10). Client-only now does the same for the queue: stacks into the inventory (a shift-drag over tiles, repeated shift-clicks) queued in a row are one job (`StorageActions.StackTakes`, `TakeJob` mode `STACKS`) that visits the containers holding any of them nearest first, a stack of each tile per step, each container opened once. Whole-stack put-aways of the same item queued in a row (a shift-double-click, Ctrl+scroll up) are one `PutAwayJob` that shift-clicks the stacks into each container in turn until it's full, then goes on to the next. Put-aways of different items stay separate jobs, since each item ranks the containers its own way. Takes onto the cursor stay one each.
- **No pause when a recipe runs out of direct ingredients.** Three things got in the way: (1) vanilla's recipe book ignores a second click on a recipe it counts as not craftable, and its count holds still while the player clicks, so clicks were dropped before the mod saw them; for crafting, every click now goes through (`RecipeBookComponentMixin`, `tryPlaceRecipe`), and one that can't craft just shows the ghost again. (2) In server mode, intermediates were only planned for recipes the book showed as needing them, and the book holds still while clicking, so clicks after the ingredients ran out went without steps and failed; every click now plans its steps from the live data (empty for a direct craft). (3) In client-only mode, merged clicks the direct ingredients only partly covered crafted that many and dropped the rest; now the intermediates planner is asked for all of them, and whichever crafts more is used.
- **"Crafting stopped partway" (client-only, Fast speed).** After shift-clicking a round's result, the job waited 2 × latency for the server, which is 0 in singleplayer, so it went by the client's own prediction (one craft, result slot empty) and placed the next step right away. When the server had stopped early because the inventory was full, that grid still held the last round, the next recipe couldn't be placed, and after 2 seconds the job gave up. It now waits at least 100 ms on Fast too, and a round counts as crafted only once the result slot is empty and no full set is left in the grid; still holding the result after the timeout says "inventory full". The user saw it with a recipe craftable both via intermediates and with ingredients out of reach, with "Exact amounts" off (whole stacks filled the inventory); that's the likely cause, not confirmed.
- **Leave one and shulker boxes.** A tile with only the kept ones loose and more in shulker boxes said "only the one left in each container" instead of taking a box; it now counts as only in boxes when nothing loose is takeable (`StorageActions.onlyInBoxes`), for clicks and the tooltip.

The user confirmed all of that worked, then (Nov 9):
- **Shift-double-click at Normal speed (client-only).** While a background job runs, clicks on the screen are held back except on the panel and the recipe book, so they can't land in the hidden container's menu. At Normal speed the first stack's put-away was still running when the double-click's second click came, so it was dropped and only one stack went. A shift-click with the put-away button on a main-inventory slot (panel showing) now goes through too (`PanelHooks.queuesPutAway`): it only queues a request, and the click guard still stops anything that would reach the hidden menu.
- **Only takeable** (`onlyTakeable`, main page, default off). The panel counts only what a take could bring out (`StorageIndex.onlyTakeable`): in client-only mode only containers within reach, and with "Leave one" on not the one each container keeps (`takeableCounts`); items only in the inventory and boxes the player carries get no tile of their own. In server mode everything in range can be taken, so only "Leave one" changes anything there. Off where nothing can be taken (the server turned taking off), as the panel then only shows where things are. The grid recounts every second anyway, so walking up to or away from storage shows within a second. An empty grid says "Nothing to take within reach" when containers are remembered but none is in reach. The recipe book is unchanged (it already marks out-of-reach recipes). Both verified in-game Nov 9.
